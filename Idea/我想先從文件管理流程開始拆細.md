# 我想先從文件管理流程開始拆細

v0 的「文件管理流程」可以拆成四條主線：建立結構、上傳/版本控管、權限與可見性、審核與追蹤。下面用「步驟 + 使用者視角」幫你展開。

***

## 一、建立資料室結構（由 0 到可用）

**角色：Originator Owner / Admin**

1. 建立 Pool 後自動產生預設資料夾
    - 系統根據私募信貸 DD checklist，自動建立資料夾：Legal / Financials / Collateral / KYC (Borrower) / Insurance / Reports / Misc。[^1][^2]
    - 每個資料夾在鏈上有一個 folderId（但可以先不獨立成物件，只當 metadata）。
2. 設定文件 checklist（可選但很重要）
    - 在每個資料夾下，系統顯示建議清單，例如：
        - Legal：Loan Agreement, Security Agreement, Intercreditor Agreement…
        - Financials：Audited FS, Management Accounts, Cashflow Projections…
    - 使用者可以勾選「本案需要哪些項目」，變成本 pool 的專屬 checklist。
    - 這些 checklist 項目存在鏈下 DB 或 Walrus，並和 DataRoom 關聯。
3. 測試權限（before share）
    - Admin 可以用「Preview as Viewer」檢查看不到權限設定頁、無法刪檔，只能讀。[^3][^1]

***

## 二、上傳／版本管理（核心 CRUD 流程）

**角色：Originator Owner / Legal / Risk（有 Editor 權限）**

1. 上傳新文件
    - 使用者在某資料夾點「Upload document」，可一次選多檔。
    - 對每個檔案，填寫：
        - 類型（從 checklist 選：Loan Agreement / Audited FS / etc.）
        - 描述（選填）
        - 關聯 checklist 項目（例如「Loan Agreement – Final Draft」）。
    - 前端加密 → 傳 Walrus → 拿到 content hash / CID。
    - 在鏈上寫入 Document metadata：
        - docId、folder、type、version=1、hash、uploader、uploadedAt、status=`NotReviewed`。
2. 版本更新（取代舊 PDF，但保留歷史）
    - 在文件列點「Upload new version」。
    - 流程與上傳相同，但：
        - version += 1
        - old version 標記為 `Superseded`。
    - UI：
        - 只在列表顯示最新版本（v3）。
        - 點進去可展開「Version history」，看到 v1/v2 的 hash、上傳者、時間。
    - 這種 version tracking 是 VDR 的標配，也是你要跟 Web2 體驗對齊的地方。[^4][^5]
3. 刪除／撤回（v0 建議限制）
    - 正式盡調中，文件不允許真正「刪除」，只能：
        - 標記為 `Archived`，從預設列表隱藏。
        - 事件寫入 audit log。
    - 目的是保護審計軌跡，避免「把不利文件刪掉」。[^6][^5]

***

## 三、權限與可見性（誰看得到什麼）

**角色：Originator Owner / Admin**

1. 基本權限模型（v0 簡化版）
    - Pool 層級角色：
        - Owner：全權（管理成員、上傳、變更狀態）。
        - Editor：可上傳/更新文件、加 comment。
        - Viewer：只能看（無法上傳、無法改狀態）。
    - 權限存在 Seal policy：
        - 以 (poolId, address) → role 映射。
        - 讀寫文件前先查 Seal。
2. Folder / Document 細粒度控制（先支援最簡常見案例）
    - v0 可以只支援「全 pool 共享」，但預留：
        - 某些資料夾（例如 Borrower KYC）只能給 Internal Risk + Legal 看。
    - 方式：
        - 在 folder metadata 設定允許的角色範圍（Owner + Legal + Risk）。
        - 產生對應的 Seal policy condition。
    - 未來可擴充到 IP 限制、時間限制等，但 v0 不做。[^7][^8]
3. 下載／列印限制（v0 可先不做 UI，但預留 flag）
    - Document metadata 可有 flags：`allowDownload`, `watermarkRequired`。
    - 前端根據 flag：
        - 禁止下載，只允許線上 viewer。
        - 顯示動態浮水印（地址 / 時間）。[^5][^7]

***

## 四、審核與追蹤（讓 DD 流程可見）

**角色：Legal / Risk / 外部顧問 / Owner**

1. 文件審核狀態流程
    - 每個 Document 有一個簡單狀態機：
        - `NotReviewed` → `InReview` → `Reviewed`（可多個 reviewer）
        - `NeedsRevision`（退回）
    - 操作方式：
        - Reviewer 打開文件，在右側 panel 選擇狀態。
        - 可以附上簡短備註（例如「缺少簽名頁」）。
    - 審核狀態存在鏈下 DB 或 Walrus，並在 Document metadata 存當前 aggregate 狀態（方便前端快查）。[^1][^6]
2. Comments / Q\&A
    - v0 可以採最簡單模式：
        - 對整份文件留言（thread），不做逐行註解。
        - 留言內容存在 Walrus / DB。
        - Document metadata 只存 commentThreadId + lastCommentAt。
    - UI：
        - 展示時間戳、作者、留言。
        - 可以 @其他成員（通知）。[^9][^1]
3. Checklist 完成度追蹤
    - 在 pool 頁面顯示整體進度條：
        - 例如：「必須文件 25 項，已上傳 20 項，已 Reviewed 15 項」。
    - 算法：
        - 將 checklist 項目與 Document 關聯。
        - 依據每個 Document 的狀態（已上傳 / 已 Reviewed）計算完成度。
    - 這種「DD checklist + 狀態」是傳統 VDR DD 流程的關鍵，也讓你的 Data Room 更像 deal 中樞，而不是單純檔案櫃。[^10][^3][^1]
4. Audit log（誰對文件做了什麼）
    - 每個重要操作都記錄：
        - `DocumentUploaded`（docId, version, actor, timestamp）
        - `DocumentVersioned`
        - `DocumentArchived`
        - `DocumentReviewed`（舊狀態、新狀態、actor）
        - `CommentAdded`（docId, actor, timestamp）
    - 前端在 Document 頁面的「Activity」tab 顯示活動時間軸。
    - 對照業界作法，這種 log 是 DD 必備，方便事後查責和稽核。[^6][^4][^5]

***

## 五、從文件管理串回資產池狀態

文件管理不是孤立的，而是驅動「Pool 狀態機」的前提：

- 當「所有必需文件都已上傳」時，系統可以提醒 Owner「可以開始 DD」。
- 當「所有必需文件都至少到 `Reviewed`」時，允許送交 IC。
- 當「指定類型文件（例如 loan agreement final）沒有 `Reviewed` 版本時」，禁止把 Pool 標為 `Ready_To_Issue`。

這種「文件狀態 → Pool 狀態」的關聯，是你跟一般檔案庫最大不同，也是私募信貸 RWA 會願意為你付錢的地方。[^11][^12][^13]

***

如果你願意，下一步我們可以挑其中一段再往下拆：

- 「上傳＋版本管理」的具體畫面和欄位，
- 還是「Checklist + 完成度」的設計（這會直接影響你怎麼賣給機構）。
