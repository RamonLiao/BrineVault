# v0版本的詳細使用者流程是什麼

v0 版本可以想成「只做資產池上線前的盡調資料室」，但整個流程從「建立 pool 專案 → 上傳與審核文件 → 切換狀態」都跑在你的平台上。下面用「使用者旅程」來拆給你看。

***

## 0. 事前假設

- 只支援：**一個 Originator 為某個 loan pool / credit facility 建立資料室並完成內部盡調**（不碰投資人、募資、還款）。
- 底層：
    - 每個 pool 一個 SUI 物件（PoolObject）。
    - 連到一個 DataRoom 物件，裡面是一堆 Document metadata。
    - 實際檔案存在 Walrus，讀寫都經過 Seal policy。
- 主要角色：
    - Originator Owner（建立 pool 的 PM/BD）
    - Internal Risk / IC 成員
    - Legal / Structuring
    - 外部顧問（選配：會計師、評等機構、law firm）

***

## 1. 建立新資產池專案（Create Pool \& Data Room）

**使用者：Originator Owner**

1. 登入平台（連接錢包或 SSO + 綁定地址）。
2. 點「Create new Private Credit Pool」。
3. 填寫基本資訊表單（存在 PoolObject meta）：
    - Pool name（例如：“SME Loan Pool 2026-01”）
    - Borrower / SPV 名稱
    - 預計 pool size（例如 20M USDC）
    - 幣別、預計到期日、jurisdiction
    - 簡短描述
4. 按「Create」，後端：
    - 在鏈上建立 PoolObject，狀態 = `Draft`。
    - 建立對應 DataRoom 物件。
    - 為該 pool 生成 Walrus 的資料根目錄。
    - 建立預設 Seal policy：只有建立者地址可讀寫。

**結果**：

- 使用者被帶到此 pool 的「Overview」頁。
- 左側看到資料夾結構（Legal / Financials / Collateral / Reports / Misc）。
- 上方顯示當前狀態：`Draft`。

***

## 2. 邀請團隊與設定權限（Share \& Roles）

**使用者：Originator Owner**

1. 在 Pool Overview 點「Manage Team」。
2. 輸入要加入的成員（錢包地址或已註冊帳號）：
    - 指定角色：`Editor`（Legal, Risk）、`Viewer`（外部顧問）。
3. 送出後：
    - 更新 Seal policy：對這些地址開啟對應權限（讀/寫）。
    - 鏈上記錄一筆「AccessChanged」事件。

**結果**：

- Legal / Risk 等人登入後，可以在「My Pools」看到被分享的 pool。

***

## 3. 上傳與整理盡調文件（Upload \& Organize Documents）

**使用者：Originator Owner、Legal、Risk（有 Editor 權限）**

1. 在 Data Room 視圖選擇資料夾（例如「Legal」）。
2. 拖拉或點選上傳：
    - Loan agreement draft
    - Security agreements
    - SPV 設立文件
    - 借款人公司登記／股權結構
    - 保險／抵押品文件
    - 初版 credit memo / risk report
3. 每個檔案上傳時：
    - 前端將檔案加密，傳到 Walrus。
    - 鏈上建立一個 Document metadata：
        - docId、fileHash、fileType、folder、uploader、uploadedAt、version = 1。
    - 該 Document 連到 DataRoom。
4. 如需更新版本：
    - 使用者在該文件點「Upload new version」。
    - 產生新 version 記錄（version = 2），保留前版記錄，顯示 version history。

**結果**：

- 所有盡調文件集中在同一個 Data Room，版本與上傳者清楚可見。

***

## 4. 內部審閱與溝通（Review \& Comments）

**使用者：Legal / Risk / 外部顧問**

1. 在文件列表中打開某個檔案（例如 loan agreement）。
2. 右側有「Review panel」：
    - 狀態：`Not Reviewed / In Review / Approved / Needs Revision`。
    - 可留言（comment），標記自己。
3. Legal 對 loan agreement 設為 `Needs Revision`，並留言「新增 cross-default 條款」。
4. Originator 收到通知，在本地編輯後，上傳新版本（v2）。

**技術處理**：

- 文件審閱狀態存在 Document metadata 或鏈下 DB，對應 hash \& version。
- 留言本身可以存在 Walrus 或 DB，鏈上只存 comment thread 的 ID 以做完整性對照。

**結果**：

- 每個關鍵文件都有：最新版本、審核狀態、留言記錄。

***

## 5. 資產池狀態從 Draft → Due Diligence In Progress（開始正式盡調）

**使用者：Originator Owner**

1. 當初步文件上傳完，Originator 在 Overview 點「Start Due Diligence」。
2. 彈出確認對話框，說明：
    - 狀態將從 `Draft` → `DD_In_Progress`。
    - 鏈上會記錄 event。
3. 使用者確認後：
    - PoolObject.state = `DD_In_Progress`。
    - emit `PoolStateChanged(Draft, DD_In_Progress, actor, timestamp)`。

**結果**：

- UI 頂部狀態標記為「Due Diligence In Progress」。
- 未來 token 發行合約可讀取這個狀態，確認 pool 尚在盡調。

***

## 6. 盡調完成並提交投審會（DD 完成 → IC Review）

**使用者：Internal Risk / Investment Committee Secretary**

1. 當所有必需文件都標為 `Approved` 或 `Reviewed`，系統可以顯示「DD Checklist 完成度 100%」。
2. Risk 在 Overview 點「Submit to Investment Committee」。
3. 彈窗顯示：
    - 必備文件 checklist（都已勾）。
    - 可以附上 IC memo PDF。
4. 送出後：
    - 上傳 IC memo 到 Data Room（Reports / IC）。
    - PoolObject.state = `IC_Review`。
    - emit `PoolStateChanged(DD_In_Progress, IC_Review, actor, timestamp)`。

**結果**：

- Pool 進入 IC 審查階段，IC 成員可以在同一資料室查看所有文件。

***

## 7. 投審會決議：Approve / Reject / Request Changes

**使用者：IC 成員（有特定角色／地址）**

1. IC 成員登入後，在「IC Inbox」看到待審 Pool A。
2. 點進去：
    - 頁面顯示：key facts（size, tenor, borrower）、風控重點、文件列表、IC memo。
3. IC 可以：
    - 點「Approve」
    - 點「Reject」
    - 或「Request Changes」並附註原因。

**系統行為**：

- 如果 `Reject`：
    - PoolObject.state 回到 `DD_In_Progress` 或標為 `Rejected`（看你怎麼設計）。
    - emit `ICDecision(Rejected, reason, actor, timestamp)`。
- 如果 `Request Changes`：
    - PoolObject.state = `DD_In_Progress`。
    - 在 Overview 顯示「IC 要求補件，列表：…」。
- 如果 `Approve`：
    - PoolObject.state = `Approved_Internal`。
    - 上傳 IC 決議 PDF，綁定這次決策。
    - emit `ICDecision(Approved, actor, timestamp)` 與 `PoolStateChanged(IC_Review, Approved_Internal, actor, timestamp)`。[^1][^2]

**結果**：

- 所有投審會決議與文件都被永久關聯到這個 pool。

***

## 8. 準備發行：Approved_Internal → Ready_To_Issue

**使用者：Originator Owner / Legal**

1. IC 通過後，Legal 進行最終檢查：
    - 所有關鍵合約文件已上傳最終版並標為 `Approved`。
    - 重要條款摘要（rate, tenor, collateral, covenants）已在 metadata 裡填好。
2. 在 Overview 點「Mark as Ready to Issue」。
3. 彈窗顯示：
    - Checklist：IC Approved、法律文件 final、重要 meta 完整。
4. 確認後：
    - PoolObject.state = `Ready_To_Issue`。
    - emit `PoolStateChanged(Approved_Internal, Ready_To_Issue, actor, timestamp)`。

**結果**：

- 之後任何「發行／tokenization 合約」都可以檢查：只有 state = `Ready_To_Issue` 的 pool 才能被用來鑄造資產池 token。
- 你的 v0 就完成「origination / assessment」階段的 on-chain 流程對接，對照現在 onchain credit 的典型 lifecycle。[^3][^1]

***

## 9. 系統背景：審計軌跡與查詢

整個 v0 過程中，你的平台會自動記錄：

- Audit log 事件（可查詢）：
    - `PoolCreated`
    - `AccessChanged`（誰被加入/移除，角色變動）
    - `DocumentUploaded` / `DocumentVersioned`
    - `DocumentReviewed`
    - `PoolStateChanged`
    - `ICDecision`
- 前端提供：
    - 每個 pool 的「Activity」tab，可以按時間軸顯示所有事件。
    - 點任何事件可以看到相關檔案／決策 PDF。

這與業界對「on-chain credit 要有完整可稽核的 operational trail」的要求是一致的，只是你把重心放在文件與合約層。[^4][^5][^6]
